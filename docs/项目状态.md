# 项目状态

> 给下一次对话的交接文件。最后更新：2026-09-27

## 一句话

VideoToLive 是一个 macOS 应用，把视频转成 Apple Live Photo 并写入「照片」App。
卖点是**视频轨不重新编码**，输出码流与源片段逐字节一致。

- 仓库：https://github.com/xLuckww/VideoToLive （公开，MIT）
- 最新版本：v1.0.0，DMG 已发布在 Releases
- 分支：`main` 之外有两条**尚未合并**的分支，都在本地、没有推送：
  - `fix/heic-444-cover`：HEIC 封面修复，以及一次已撤回的竖屏重编码（见下文「踩过的弯路」）
  - `feature/batch-history`：从上面那条拉出，批量队列与历史记录。合并它就包含了两条的全部内容

## 不能破坏的技术约定

这几条一旦改错，功能会**静默失效**——不报错，但产出的文件不是合格的 Live Photo。

1. **passthrough 的两个 nil。** `AVAssetReader` 与 `AVAssetWriter` 两端的 `outputSettings`
   都必须是 `nil`，只要有一端不是，就会走重新编码。见 `LivePhotoVideoWriter.remux`。
2. **不要用 `AVAssetExportSession`。** 它无法写入自定义定时元数据轨，这正是其他同类工具
   只能退回重新编码的原因。
3. **配对三要素缺一不可。** 静态图 Maker Note 键 `17`、MOV 的 `content.identifier`、
   MOV 的 `still-image-time` 定时元数据轨，三者用同一个 UUID。第三条最容易漏，
   漏了之后照片 App 可能仍识别为实况，但长按播放时的静止画面位置不对。
4. **抽帧容差必须显式设为 `.zero`。** 否则会拿到邻近帧，表现为「按方向键画面不变」。
5. **吸附只在编排层算一次。** `LivePhotoConverter.convert` 算出区间后，封面挑选和视频封装
   共用同一个区间。之前两边各算各的，导致封面帧落在成品之外。那里留了一条不变式断言，
   封面帧不在成品区间内会直接报错，不要删掉。
6. **HEIC 封面质量不能取到 1.0。** 恰好 1.0 时 ImageIO 会编成 4:4:4 的 HEVC Range Extensions，
   Mac 能软解、iPhone 解不了，iCloud 同步后提示「加载此照片的更高质量版本时出错」。
   `CoverImageFormat.maxQuality` 把 HEIC 钳在 0.99，那里是标准 4:2:0。
   检查办法：`exiftool -ChromaFormat -GeneralProfileIDC 封面.heic` 应为 `4:2:0` 与 `Main` / `Main 10`。
7. **取消要能停在半路，并清理产物。** 队列的取消依赖两处：`LivePhotoConverter.convert`
   在阶段之间检查取消，`LivePhotoVideoWriter.remux` 在取消时停掉读取端。
   转换失败或取消时整个产物目录会被删掉，别把这个清理挪到成功路径之后。

## 环境限制

这些是踩过的坑，换台机器或换人接手会再遇到。

1. **没有安装完整 Xcode，只有 Command Line Tools。** 所以 SwiftUI 的 `@State`、`@FocusState`
   这类宏**不能用**，它们的宏插件只随完整 Xcode 分发。现有代码把所有界面状态都放在
   `AppModel` 里绕开了这个限制，包括拖拽过程中的临时值。继续写界面时要沿用这个写法，
   或者装完整 Xcode。
2. **macOS 文件系统默认不区分大小写。** 命令行工具叫 `vtl` 而不是 `videotolive`，
   就是因为后者会和 App 目标 `VideoToLive` 的源码目录、编译产物冲突。
3. **App 是 ad-hoc 签名，没有经过 Apple 公证。** 用户第一次打开需要手动允许。
   签名变化会导致照片图库权限需要重新授权。
4. **`gh` 命令行当前认证已失效**（返回 401）。需要推送或操作 Releases 时，
   先运行 `gh auth login`。普通 `git push` 和 `git fetch` 目前仍然可用。

## 踩过的弯路：iPhone 上实况「发糊」

2026-09-26 到 27 日花了很多轮排查，结论写在这里，**别再重走一遍**。

- 现象：写入图库、经 iCloud 同步后，在用户自己那台 iPhone 的相册 App 里长按播放，
  视频部分明显发糊，静态封面清晰。竖屏更明显，横屏其实也糊，只是在竖着拿的手机上显示得小。
- 真正的原因不在文件：同一张实况隔空投送到**另一台 iPhone**、发给别人、投到平板，都是清晰的。
  糊出在那台手机相册 App 播放实况时所用的版本上，改编码治不了。
- 走过的弯路：曾以为是「原生竖屏存储」导致，把竖屏素材改成横屏存储加旋转、重新编码
  （`a8d7c2f`），后来撤回（`61f18f5`）。它只让效果稍好一点，却让竖屏素材丢了无损。
  同规格的测试片还出现过一清一糊，说明手机端的表现本身就不稳定，不能拿来判断文件好坏。
- 期间顺带发现并修掉的真问题只有一个：HEIC 质量 1.0 的 4:4:4 封面（上文约定第 6 条）。
- 以后再有人报「iPhone 上糊」：先让对方把那张实况隔空投送到另一台设备上看。
  那边清晰，就是设备端的问题，不要改编码。

## 怎么验证改动没有破坏无损

改完核心库后，跑这三步：

```bash
swift build -c release

# 1. 转换一段测试素材
.build/release/vtl convert 视频.mov --start 11 --duration 5 --cover auto --out ./out --no-import

# 2. 检查配对三要素，应当看到 4 个 ✅
.build/release/vtl verify out/*/*.mov out/*/*.heic

# 3. 逐帧比对码流：在源里找到成品的首帧，之后每一帧的哈希都要相同
ffmpeg -v error -i 视频.mov -map 0:v:0 -c copy -f framemd5 - | grep -v '^#' | awk -F', ' '{print $6}' > src.txt
ffmpeg -v error -i out/*/*.mov -map 0:v:0 -c copy -f framemd5 - | grep -v '^#' | awk -F', ' '{print $6}' > out.txt
i=$(grep -n -m1 -F "$(head -1 out.txt)" src.txt | cut -d: -f1)
sed -n "${i},$((i + $(wc -l < out.txt) - 1))p" src.txt | cmp - out.txt && echo 逐帧一致
```

第 3 步不要用 `-ss … -t … -f md5` 比整段：ffmpeg 流复制时的起止帧和成品对不齐，
即使码流完全一致两行 MD5 也会不同。

测试素材可以用 ffmpeg 现造：

```bash
ffmpeg -f lavfi -i "testsrc2=size=3840x2160:rate=30:duration=20" \
  -f lavfi -i "sine=frequency=440:duration=20" \
  -c:v hevc_videotoolbox -b:v 40M -tag:v hvc1 -g 60 -pix_fmt yuv420p \
  -c:a aac -shortest testdata/4k_hevc.mov
```
